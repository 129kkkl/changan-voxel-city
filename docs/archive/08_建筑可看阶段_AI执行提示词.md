## 二、这一次的美术目标

核心概念：**有清楚建筑秩序的盛唐微缩城。远处是连续而有层次的瓦顶，中景是能辨认功能的院落组团，近处是有厚度、有开口、有支承关系的建筑。**

观看路径应当成立：全城鸟瞰辨认轴线与地标 → 降到坊上辨认主院、侧院与小巷 → 落到门前看见台阶、门洞、檐下空间和柱墙关系 → 沿街走到下一处不同的建筑群。

主动不做三件事：

1. 不靠灯光、浓雾、景深或夜景掩盖粗糙形体。
2. 不先堆灯笼、旗帜、树木、瓦片和斗栱数量，留下不变的盒子。
3. 不只做几栋漂亮地标，继续让普通住宅和街巷停留在基底水平。

明确风格为体素微缩建筑，而非写实扫描。保留块面语言，但不能把所有构件都压缩到同一粗格。年代与建筑形制的具体判断，采用可靠研究或建筑实物资料交叉核对；后世遗存只能作为有说明的参照。无法确认的内容标为艺术化推定，禁止把效果图当作考古证据。研究服务建模，不要让资料整理取代实现。

## 三、先解决表达尺度，禁止重演双层失败

现有规格记载水平一格约对应 13.8 米、竖向另作夸张。这是全城压缩口径，不足以自动支撑门窗、柱列和檐口。现有 `proto.hall` 默认墙高约四格；即使已有屋顶类型分支和构件函数，也必须判断输出是否在画面中可读。

开始批量改造前，用一页简短决策记录说明：普通房屋在常用机位有多大、现有格距能否表达开间、墙柱分离和屋檐厚度、哪些结构需要更细的局部几何。用真实样板验证选择，不能凭参数名称宣布方案可行。

允许城市骨架使用粗体素、建筑采用更细的局部体素或合并网格；关键是**每栋建筑只有一个权威生成来源**。不要为了细化而把整个世界稠密分辨率整体翻倍。

- 替换某类建筑时，在源头停止其旧几何输出，再从同一布局记录生成新建筑。
- 禁止旧建筑生成完再叠一套细建筑，随后通过颜色、包络、mask 或大范围删除补救。
- 不得误删共用地形、道路、墙体、铺装、门墩或树木。写清各类构件的所属关系。
- 如果分阶段迁移，新旧生成器只能负责互不重叠的建筑对象；同一对象不得重复输出。临时并存不等于叠加。
- 碰撞、拾取、编辑、保存恢复与 LOD 必须反映新建筑，不能只让画面变细，交互仍打在旧盒子上。
- 不要先开发庞大的通用建筑框架。先打通最小的“布局记录—唯一建筑输出—可见模型—交互”闭环，再扩展。

## 四、建筑至少做到这些可见改变

### 1. 屋顶首先具有正确的轮廓

让普通住宅、重要厅堂、楼阁的屋顶在轮廓上就有区别。悬山、歇山、庑殿等采用适用的形制，不能只换枚举或颜色，最后仍是相同的矩形层层收缩。

普通屋顶应看见两坡、屋脊、山面与连续出檐；重要厅堂应看见更舒展的屋身比例和有组织的转折。控制屋面坡度、檐口厚度、屋脊高度和端部收头，避免金字塔、厚蛋糕、巨型黑盖子。不要给每栋民居都安重檐或夸张翘角。

重檐建筑必须有可理解的上下层结构，中间留出真实楼身，不能两张屋顶互相穿插。优先保证轮廓，瓦垄只在能看见且预算允许时添加。

### 2. 墙、柱、檐下空间分得开

立柱应有体积并承担屋顶，墙面相对柱列有合理退进；不能用几条红色色带冒充柱网。开间是重复且有主次的结构节奏，不是随机窗格。

门洞真实可见并与道路、台阶相接。窗洞有深度，不能是贴在实墙上的黑色噪点。廊子应看得出可以通行，不能被墙填实。斗栱可概括成少量支承块，但必须位于柱头与檐下的合理位置，不形成悬空方块。

### 3. 台基与院落构成完整建筑群

重要建筑有承接屋身的台基和台阶；普通宅院保持朴素。台基不可与屋身漂离，也不可被新生成器切掉。

院落是真实留空的空间，由主房、厢房、门屋、院墙共同组织。主房与附属房在跨度、高度、屋顶和朝向上有层级。小宅、大宅、寺院、市肆不能只是同一个合院缩放。

围墙高度应与建筑和观看机位相协调，避免漫游只看见连续高墙。保留合理围合，不以拆掉全部院墙换可见性。

### 4. 色彩帮助读懂结构

灰瓦、木构、浅墙、夯土、石台各有清楚的明度层次，延续现有调色方向。檐下可以暗，但不能全黑到吞掉柱墙；灰瓦不能整片死黑或漂白。

颜色变化按建筑用途、等级和成组修缮差异组织，禁止每格随机着色。朱色与装饰有所节制，不把全城做成宫殿。先在清晰日光下成立，再检查晨昏与夜景。

坊内保持长安总体规整，变化发生在坊内宅地和建筑群：主院与小院穿插、巷口局部退让、沿街屋顶连续但不等长、寺院或府第形成明确主次。不要把房屋随机旋转来伪造自然感，也不要把全城改成欧洲曲街小镇。

**阶段 B：做出普通建筑样板。**

打通唯一生成来源，完成小宅、宅院、店肆，先解决屋顶、柱墙、开口和空间比例。退出条件：真实浏览器中，比基线明显更像完整建筑；不能靠标签才能知道门、廊或院子在哪里。

**阶段 C：全城替换与层级完善。**

完成其余样板，推广到所有普通坊与特殊建筑入口；修正地块容纳、出檐冲突、道路侵占和建筑群主次。退出条件：全城恢复完整密度，随机抽取普通坊也达到样板语言，没有仅样板漂亮的情况。

**阶段 D：稳定交付。**

优化合批、不可见面和远景细节，修复 LOD、碰撞及编辑问题。运行适用于现架构的已有测试，检查测试是否误引用冻结的细建筑实验模块；新增测试只覆盖实际新风险，不为旧错误行为补 PASS。不得通过放宽阈值或删除内容解决失败。

构建单文件并完成下述画面与交互检查，再更新必要文档。只有这一阶段完成，才能说任务完成。

## 七、证据要少而有用

不要生成几十页自评，也不要把确定性测试当美术验收。

固定一个主种子，以相同机位、分辨率和清晰日照做上述六类前后对照；另用两个种子抽查普通坊、市肆与地标，排查布局和碰撞偶发问题。浏览现有十八景，检查穿模、屋面遮挡及机位失效，不必为每个重复场景制作冗长报告。

重点回答：

1. 鸟瞰仍有连续瓦顶，且主次分明，是否保住了城市规模和密度？
2. 普通坊中景能否读出建筑群、院子与街巷，而非等距盒子阵列？
3. 近景门洞、台阶、柱墙和屋檐是否真实存在并彼此合理？
4. 是否还有双层重复建筑、浮空块、黑色屋顶、断台基、封死通道或互穿屋檐？
5. LOD 切换是否保持屋顶轮廓和主要空间，不让建筑突然缺块？
6. 离线启动、种子重建、导航漫游、昼夜及原有编辑保存是否仍可用？

性能按当前项目预算评估，记录实际运行环境和代表场景；静态批次估算不能称为实测 FPS。优化顺序优先考虑网格合并、共享材质、不可见面剔除、细节距离分级，保留中远景建筑主体与屋顶。

本地 HTTP 和 `file://` 分开记录。截图必须来自实际运行产物，不能用绘图、数据俯视图、离线渲染示意或生成图片冒充。环境无法运行或截图时，明确写“视觉待验”，交付可运行代码与复验入口，不得声称已达到可看标准。
